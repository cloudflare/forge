Generated code is easiest to trust when CI regenerates it and checks the result. This guide sets up
a check that fails when the committed SDK does not match the document, with GitHub Actions. The same
steps work in any CI.

## 1. Pin the version

Install `@cloudflare/forge` from npm and pin an exact version in `package.json`. Even a bug fix can
change generated output or surface a new error, so review Forge upgrades alongside their output:

```json title="package.json"
{
  "devDependencies": {
    "@cloudflare/forge": "0.3.0"
  },
  "scripts": {
    "generate": "rm -rf sdk && forge generate openapi.json --target ts --out sdk"
  }
}
```

Remove the output first: Forge overwrites files but never deletes ones it no longer generates, so a
removed group would otherwise leave its files behind.

## 2. Add the check

Regenerate, then fail if anything changed:

```yaml title=".github/workflows/sdk.yml"
name: SDK
on: [push, pull_request]

jobs:
  generate:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 26
      - run: npm ci
      - run: npm run generate
      - run: git add --intent-to-add sdk && git diff --exit-code -- sdk
      - run: npx tsc --noEmit
```

The last step type-checks the SDK with your project's `tsconfig.json`. The SDK writes none of its
own.

`git diff --exit-code` fails with the diff in the log when the document changed and the SDK was not
regenerated. `git add --intent-to-add` comes first so that new files, such as a new group's, are in
the diff too.

The `timeout-minutes` matters for plugins: Forge does not time out a WebAssembly plugin, so one that
loops would hold the job.

## 3. Verify the check

Push the workflow with an up-to-date SDK. The job passes: `git diff --exit-code` prints nothing and
exits with status 0, and so does `tsc`.

To see it catch a stale SDK, change a summary in the document without regenerating, and push. The
job fails at the diff step with status 1, and the log shows the lines of the SDK that would change.

Forge also exits with status 1 for any error in the document or a plugin, and prints every document
error at once, so the log is a complete list of what to fix. Refer to
[Troubleshooting OpenAPI documents](/openapi/errors/).

## Plugins in CI

Build the plugin in the same job, before generating, so the check always runs the plugin as it is in
the commit:

```yaml
      - run: npx forge-plugin build plugins/docs.ts --out plugins/docs.wasm
      - run: rm -rf docs/api && npx forge generate openapi.json --target wasm://plugins/docs.wasm --out docs/api
```

A Rust plugin needs `rustup target add wasm32-wasip2` first.

## Forge from source

To run an unreleased Forge, build it with the `wasm` feature if you run plugins:

```sh
cargo install --git https://github.com/cloudflare/forge --features wasm
```

Or point the package's launcher at any binary with `FORGE_BINARY`:

```sh
FORGE_BINARY=/path/to/forge npx forge generate openapi.json --target ts --out sdk
```
